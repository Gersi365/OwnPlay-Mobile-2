Verified source defects and risk factors
1. Stage 11 provider-source contract and Android runtime network policy were inconsistent.
   - OwnPlay source validation intentionally accepted both http:// and https:// Xtream and remote M3U/M3U8 locators.
   - The Stage 11 Android manifest did not permit cleartext HTTP traffic.
2. Refresh diagnostics were too lossy.
   - Provider failures previously collapsed into a generic Refresh failed presentation.
3. CPU-heavy provider catalog transformation could resume on the caller/Main dispatcher.
   - ProviderHttpTransport itself uses asynchronous OkHttp callbacks, but JSON parsing and provider-to-domain catalog mapping executed after suspension on the caller context.
   - A large Xtream response could therefore monopolize the UI thread during parse/map work.
4. Large provider collections were eagerly composed.
   - Live used a vertically scrolling Column and channels.forEachIndexed, causing every Live channel row to be composed eagerly.
   - Library Movies, Series, and Downloaded Media used horizontalScroll Rows with forEach, causing every item in those collections to be composed eagerly.
   - Large real-world Xtream catalogs can contain thousands of entries, making those structures unsuitable for bounded UI work.
5. The HTTP warning was technically correct but ambiguous for HTTP-only providers.
   - It recommended HTTPS when available without explicitly stating that OwnPlay supports HTTP providers.

Corrections
- AndroidManifest.xml explicitly permits cleartext traffic so runtime behavior matches the supported HTTP/HTTPS source contract.
- ProviderTransportFailurePolicy and SourceRefreshFailurePolicy retain safe, credential-free diagnostics for cleartext blocks, DNS, timeout, TLS, refused connection, HTTP status, auth-like rejection, malformed/unsupported Xtream payloads, read failures, and fallback failures.
- Failed refresh continues to preserve the last known catalog.
- SourceCatalogLoader now performs provider catalog loading, JSON result transformation, and catalog mapping inside Dispatchers.Default rather than allowing CPU-heavy catalog work to run on the Main dispatcher.
- Live browse rendering now uses LazyColumn with stable channel keys and itemsIndexed; channel rows are composed on demand instead of all at once.
- Library Movies, Series, and Downloaded Media rows now use keyed LazyRow items; large provider collections are composed on demand instead of eagerly.
- HTTP provider copy now states explicitly that HTTP is supported when a provider does not offer HTTPS, while retaining the TLS-security warning.
- Source Management labels the notice as an HTTP provider notice rather than an HTTP connection error-like state.
- Focused tests continue to cover transport classification and now assert that the HTTP warning states that HTTP is supported.

Security boundary and tradeoff
- Allowing cleartext traffic is an explicit compatibility tradeoff because OwnPlay accepts user-selected provider endpoints and some legitimate Xtream/M3U providers expose only HTTP.
- HTTP is supported but is not secure transport: credentials and traffic are not protected by TLS.
- Xtream credentials remain in Android Keystore-backed credential storage rather than Room.
- Provider URLs, usernames, passwords, tokens, and runtime credential-bearing stream URLs are not written into diagnostic messages or audit evidence.
- Transport exception text is not surfaced to the user.
- Existing URL redaction and runtime-only credential-bearing locator boundaries remain unchanged.
